## Tarea 2 — Completar documentación de consistencia

En la documentación técnica de CacheConfig y en `.orca-delivery.md`, expresar explícitamente:

- Las evicciones de ID y tracking son operaciones separadas, no atómicas entre sí. Un fallo puede dejar solo una clave invalidada.
- MySQL y Redis no comparten una transacción atómica; un fallo Redis después del commit no revierte MySQL.
- Una lectura concurrente puede repoblar datos antiguos después de invalidar.
- El TTL empieza con cada escritura Redis, no con la mutación MySQL.
- La autorización usa customerId/courierId del DTO cacheado: la ventana de obsolescencia puede conservar temporalmente acceso del repartidor anterior. No afirmar revocación instantánea bajo concurrencia.
- La solución no garantiza consistencia linealizable; los tests de reasignación validan el escenario secuencial.

Corregir la afirmación del informe sobre `git diff --check`: verifica whitespace y marcadores de conflicto, no sintaxis Java ni compilación.

## Pruebas recomendadas para el Builder

Ejecutar y evidenciar las siguientes pruebas de estabilidad y seguridad:

### PR-1 — Workflow se activa con cambio aislado

- Realizar un cambio aislado en `src/main/java` o en `pom.xml` (por ejemplo, un comentario o una dependencia sin impacto funcional).
- Ejecutar el workflow de CI/CD.
- Verificar que el job `distributed` se active y complete.
- Revertir el cambio aislado tras la verificación y no incluirlo en la entrega final.

### PR-2 — Rollback transaccional ante fallo de invalidación de caché

- Simular un fallo durante la invalidación de Redis después del commit de MySQL en una mutación (assignCourier, changeStatus o cancel).
- Verificar que MySQL no quede con persistencia parcial: el estado de MySQL debe reflejar solo el commit exitoso o el rollback completo.
- Confirmar que no hay claves huérfanas ni persistencia parcial entre MySQL y Redis.
- Documentar el comportamiento observado y la estrategia de recuperación.

### PR-3 — Redis no disponible o con timeout

- Simular Redis caído o con timeout durante lecturas y mutaciones.
- Comprobar el comportamiento HTTP de la API (códigos de estado, mensajes de error).
- Verificar que MySQL mantenga consistencia y que las mutaciones no corrompan el estado relacional.
- Confirmar que no se silencian errores de Redis sin diseño arquitectónico previo.

### PR-4 — Autorización con caché caliente

- Precargar ambas rutas (por ID y por tracking) con un usuario autorizado para calentar la caché.
- Ejecutar GET sobre las claves cacheadas con:
  - Cliente ajeno: HTTP 403 `ACCESS_DENIED`.
  - Repartidor no perteneciente al envío: HTTP 403 `ACCESS_DENIED`.
  - Roles administrativos: acceso permitido.
- Verificar que `requireRead(response)` se ejecute en cada hit, sin confiar en la caché para saltarse la autorización.

### PR-5 — Invalidación de claves tras mutaciones

- Después de cada mutación (asignación, reasignación, cambio de estado, cancelación), confirmar que ambas claves físicas (`shipment::id::{uuid}` y `shipment::tracking::{trackingCode}`) son desalojadas de Redis.
- Verificar selectividad: mutar un envío no debe invalidar las claves de otro envío distinto.
- Evidenciar con reasignación y cambio de estado.
